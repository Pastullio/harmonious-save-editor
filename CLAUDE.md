# Harmonious Save Editor

No Man's Sky save editor for Steam/GOG PC saves (Frontiers 3.60+). Owner: Pastullio. GPL-3.0.

## Layout
- `src/codec.js` — save format: LZ4 chunked data file, XXTEA-encrypted meta file, lossless JSON (keeps key order, number lexemes, escapes, raw hashed-ID bytes). Works in browser and Node.
- `src/app.html` — the whole editor UI (vanilla JS, no framework). `build.js` inlines the codec and the key mapping into it.
- `desktop/` — Go app (stdlib plus one vendored library, github.com/klauspost/compress for zstd; keep `desktop/vendor` committed and add nothing else) that serves the page on 127.0.0.1 with a per-run token and an API to list/read/write save pairs. Windows build is the main deliverable.
- `desktop/render.go` + `desktop/render_cover.py` — corvette cover renders: finds the owner's Blender and Charon Forge (Blender extension, GPL-3.0, github.com/xX-Charon-Xx/charon_forge), runs `blender -b --factory-startup --python render_cover.py`, caches PNGs in `%LOCALAPPDATA%\HarmoniousSaveEditor\covers\<build hash>.png`. Never bundle Charon Forge's game-derived models; always read the local install.
- `desktop/itemdb.go` — item names and icons from the owner's own Goatfungus `NMSSaveEditor.jar`: found on the PC (Downloads, Desktop, Documents, Program Files…), remembered in `settings.json` as `itemdb`, served from inside the jar (`/api/itemdb`, `/api/itemdb/items.xml`, `/api/itemdb/icon`). Never bundle the jar's data or icons. The browser version reads a picked jar into IndexedDB instead.
- `desktop/profiles.go` — loadout profiles as JSON files in `%LOCALAPPDATA%\HarmoniousSaveEditor\profiles` (list, write, delete, reveal). Profiles use plain key names (`toPlain`/`fromPlain` in the page) so they work with obfuscated and plaintext saves. `desktop/slots.go` — copy a save into an empty slot (never overwrites) and zip a whole account folder.
- `desktop/gamefiles.go` + `desktop/itemlib.go` — the app's own item library, built from the owner's game install: HGPAK archive reader (format from HGPAKtool, MIT), MBIN table reader (field offsets from MBINCompiler's libMBIN, checked against each template GUID), BC7/BC1/BC3 DDS decoder (port of Pillow's BcnDecode.c). Reads the product (plus base-part and customisation), substance, technology and procedural-technology tables and the English language files, converts icons to 128 px PNGs, and caches all of it in `%LOCALAPPDATA%\HarmoniousSaveEditor\itemlib`. Built automatically on first start and rebuilt when the archives change. When a game update changes a table layout the GUID check fails: update the offsets from the newest libMBIN. Goatfungus's jar (`desktop/itemdb.go`) is only a fallback now. Never commit game files.
- `desktop/models.go` — real models: SCENE.MBIN trees (REFERENCE nodes pull in parts; siblings named `_Group_Option` are alternatives, `xRARE`/`Shape`/`LODn` handled in `optionOf`), GEOMETRY.MBIN.PC / GEOMETRY.DATA.MBIN.PC streams (magic DDDD…; positions half4 at stride 16, then vertex data and indices, 16-bit per mesh whenever it has ≤65,536 vertices whatever the header says). Meshes under a JOINT are skinned and already in model space, so they skip the joint transforms. Effect meshes (glow, lights, shadow planes, decals; see `effectMaterialRe`) and shield/effect/decal references are left out. `/api/model/parts` gives the choice tree, `/api/model/mesh` one binary triangle mesh (`HSEM`; `only=<group>&depth=n` keeps just the geometry under that group's chosen option, n counting same-named groups from the outside, for the picker's part pictures). Picks are keyed by group name; a name that repeats at different depths (`_MultiTool` inside `_MultiTool`) stores one choice per depth joined with `|` (`pickFor`, `merge` in `partsDialog`). The picker (`partsDialog`) shows each choice as a tile with its own picture, nested groups indented under the choice they belong to and named without the parent's code (`partLabel`, `PART_WORDS`). The page draws it with WebGL2 (`GL3D`) and stores the owner's part picks in IndexedDB (`parts:<cover key>`).
- Coordinates page (`PAGES.coords`, `Place` in `src/app.html`): portal code (planet, system, Y, Z, X), galactic address (X+0x7FF:Y+0x7F:Z+0x7FF:system) and the packed 64-bit address used by discovery records and bases (from the low bits: X 12, Z 12, Y 8, galaxy 8, system 12, planet 4; parse with BigInt). Warp writes `UniverseAddress`, moves the old one to `PreviousUniverseAddress` and sets `SpawnStateData.LastKnownPlayerState` to `InShip`. Arriving at a base (`arrivalSpots`, `placeAtSpot`, `warpTo(p, spot)`): bases and teleport endpoints store a planet-relative `Position`; the spawn fields are star-relative, so the planet centre comes from `PlanetPositions[planet - 1]` (same order as `PlanetSeeds`). `savedPlanetCentres` only trusts them when `PlanetSeeds` matches nms-core's predicted seeds for the save's address; `rememberPlanets` keeps them in IndexedDB (`planets:gi:x:y:z:sys`) so other saves can arrive there. Player 2 m above the base centre facing its `Forward`, ship hovering 40 m up, `OnFoot`. Checked on the owner's save made at a base (121 m from where they stood). Arriving on the freighter (`placeAboard`, `ABOARD`): writes `FreighterUniverseAddress`, clears `FreighterDismissed`, state `AboardFleet`; player and ship positions are freighter-relative, copied from the owner's save made aboard a capital freighter; the death respawn point is star-relative beside `FreighterPositionInSystem`. `test/e2e/test_arrive.js <dir> <folder with a save made at a base> [other save folder] [plain JSON of a save made aboard]`. Glyph art comes from the owner's Portal Glyph Banner (`src/assets/glyphs/g0-gF.png`, inlined by `build.js`, drawn as CSS masks). `test/e2e/test_coords.js <dir>` tests it on a copy of a real save. System prediction (`predictSystem`) uses `vendor/nms-core` (MIT, unchanged copies; see its README for provenance), bundled by `tools/bundle-nms-core.js` into `NMSGEN` with the letter map gzipped (unpacked with DecompressionStream on first use). Don't use nms-core's `economy.js`, the biome/sentinel `opts` of `planetName()` or `sizes`: they aren't game-accurate.
- Dock Yard (the ship library; section id `library`, the page's "library" source is the Ship storage folder): `desktop/ships.go` (`/api/ships`, `/api/ships/file`, `/api/ships/index`, `/api/ships/folders`) keeps `Documents\Harmonious Save Editor\Dock Yard\{Ship storage,Garage,Deleted}` (an older `Ships\Library` is moved across once by `migrateShips`) and `library.json` (tags, favourites, links, notes, cached summaries keyed `src|root|path`); linked folders (`settings.shipFolders`) are read only, enforced in `shipPath`. Page: `PAGES.library`, `ShipLib`, `parseShipFile`, `putShipInSave`, `garageCapture` (runs when a save opens). A corvette's build is the `PlayerShipBase` in `PersistentPlayerBases` whose `UserData` is the ship's slot index; moving a corvette means re-pointing `UserData`. TAZ's `.nmsship` is a zip of `objects.json` (the build's Objects), `so.json` (the ShipOwnership entry) and `ccd.json` (the slot's `CharacterCustomisationData` entry; ships 1-6 are indexes 3-8, ships 7-12 are 17-22, per libMBIN's `CustomisationDataTypeEnum`); `unzip`/`zip` in the page use DecompressionStream/CompressionStream('deflate-raw'). A `.so` is just the ship entry. `test/e2e/test_library.js <dir>` covers it on a copy of a real save.
- Shipwright (`PAGES.shipwright`): corvette build tools. `partGroup` sorts parts by the game's own description ("Corvette Reactor Module", "Corvette Main Engine"…, from the item library) with ID prefixes as the fallback; `tunedOrder` is a stable sort in TAZmd's documented priority order (tazmd.nl/corvette-optimizer; our own code). Paste/load replaces a build's Objects only, keeping the base's UserData, BaseType, name and owner, and puts each part's fields in the game's order (`inGameOrder`). `addCorvette(slot)` copies a ship entry already in the save (BIGGS model, new seed, C class, empty inventories) and adds a `PlayerShipBase` (copied from another corvette base for the layout, owner taken from the player's bases) with `STARTER_PARTS`. `test/e2e/test_shipwright.js <dir>` (needs the fakebanks item library for names).
- Ship slots (`shipSlotsPanel` at the top of the Starships page): `arrangeShips(order)` (order[newSlot] = oldSlot) moves ShipOwnership, ShipUsesLegacyColours, the slot's CharacterCustomisationData entry (`shipCcdIndex`), PlayerShipBase `UserData`, `PrimaryShip` and `CorvetteEditAssociatedShipIndex` together. `shipSlotIssues()` lists problems with fixes; deleting fixes are last and marked danger. `addCorvette` = `makeCorvetteShip` + `makeStarterBase`. `test/e2e/test_slots.js <dir>`. Archived ships (`archivedHtml`, `restoreArchived`, `archiveShip`): `ArchivedShipOwnership` is a fixed list (18 in the owner's save), filled entries first (`compactArchive`); an entry is `{Ownership (the ship, Name emptied), Customisation, UsesLegacyColours, ArchivedName, ArchivedClass {ShipClass}, ArchivedInventoryClass}`. Corvettes and the current ship aren't archived here. Add buttons: `addShipDialog` (new corvette or `duplicateShip`, which copies colours, customisation and the build), `addToolDialog`, `addExoDialog` (learns the geobay blueprints found by name in the item library), `addPetDialog`; `ownedPage` takes `actions`. `test/e2e/test_add.js <dir> <folder with save2.hg pair that has archived ships>`.
- Cargo (`PAGES.cargo`): `cargoPlaces()` lists every cargo inventory (special lockers flagged and left out of consolidating by default). `consolidatePlan(dest, sources, {onlyHave, skip})` plans per item (top up the destination's stacks, then free slots, smallest source stacks first) and `applyPlan` carries it out; `moveStack`/`moveSlots` top up matching stacks before using a free slot. Drag and drop in grids: `wireDrag`/`dropOnSlot` (`DRAG`); technology never leaves its own inventory. `test/e2e/test_cargo.js <dir>` checks every item's total across all inventories stays the same.
- Small pieces: TAZ `.so` export (`soJSON`: plain keys, 2-space indent, CRLF, no BOM; matches a TAZ-written file). Place card (`placeCard`/`placeText`/`shareCard` on the Coordinates prediction). Turntable in `miniCover` (hover spins, drag turns; renders and pictures stay still). Custom covers on disk via `/api/covers/custom` (`desktop/covers_custom.go`, `Dock Yard\Covers\<sha1 of key>.<ext>` + `covers.json`), `moveCoversToDisk` moves old IndexedDB ones once. Drag-box selection in `invBlock` (starts on an empty slot or a gap; stacks drag and drop instead). Tech pack names: `techPackId` (joaat of the tech ID, little-endian, lowercase and 0x00/'#' bytes flagged in the two prefix bytes) and `addTechPacks` in `loadLibrary`. BBA `.nmsprefab` (`{Prefab: [objects]}`) loads in `parseShipFile` and the Bases page ("Add a prefab"). `desktop/linkmeta.go` (`/api/linkmeta`, public http(s) only) reads a listing's og tags for the Dock Yard's "Get art from the link". `RESOURCES` (sidebar "Other resources", `#gBanner` on Coordinates). Ship exports sit in one `details.menu` (`exportMenu`). `test/e2e/test_quickwins.js <dir> [prefab]`.
- Updates (`desktop/update.go`, `checkForUpdate` in the page): `build-desktop.sh` stamps a date version (`-X main.appVersion=YYYY.MM.DD.HHMM`) and writes `dist/version.json` (version, size, sha256, url, notes from `RELEASE_NOTES`). The app reads `defaultUpdateURL` (raw GitHub `dist/version.json`; `HSE_UPDATE_URL` overrides), offers a newer build once per version, downloads it to `<exe>.new`, checks size and SHA-256, renames the running exe to `.old` (removed on the next start), puts the new one in place and restarts it. Dev builds (`appVersion` "dev") don't check. The raw URL only works while the repo is public. `test/e2e/test_update.js <dir>`.
- Dialogs close from `#dlgX` in the top-right corner; an action labelled "Close" becomes the × instead of a footer button. Cover pages use `Covers()` (Cover Flow, or `CoverGrid` when `coverView()` is "grid", stored in localStorage `hse-cover-view`, default Cover Flow; `viewSwitch()`); the Dock Yard uses `libFlow` (covers fill in from the file near the centre). Planet table biomes come from discovery records (`systemKnowledge().biomes`, `BIOMES` = GcBiomeType).
- Help tips: descriptions sit behind a "?" (`hint(text)`, one floating `.tip-pop`); `hintify` (run by a MutationObserver on the page and dialogs) turns `p.ed-note`/`p.pred-note` into a tip on the nearest heading and long bracketed field labels into tips. Status lines that must stay visible get `data-keep`. The page's own description under its title always stays visible (owner, 2026-10-30).
- Dock Yard ship card (`libDetail`, a `customDialog`): actions grouped under the picture as Use / Picture / Export / File (`data-ld`), no footer buttons.
- Settlements: Owned | Visited switch (`B.setTab`, default Owned, which says so when you run none). Visited settlements belong to other players and are shown read-only (`ro-grid`), never editable.
- LiveLink from Blender (`desktop/live.go`, `desktop/addon/harmonious_live_link.py`, `LIVE`/`liveStart`/`liveApply` in the page): the app writes `live.json` (port, a per-run live token) in its app folder; the add-on (Blender 4.2+, save_post handler plus a "Send now" button in the 3D view sidebar, Harmonious tab) reads the build with Charon Forge's `get_builder().serialise()` or the Base Builder's `scene.nms_base_tool.serialise(objects_only=True)` and POSTs `{objects, name, file}` to `/api/live/build` with `X-Live-Token` (the only API that token opens). The page arms a corvette (`/api/live/arm`), long-polls `/api/live/next`, puts the parts on it (`inGameOrder`, tuned if Shipwright's tune-up is on) and, unless turned off, writes with `encodeSave` + `appWriteFiles` (the app backs up each time), then answers via `/api/live/result`, which Blender shows. `/api/live/addon` serves the add-on. Being linked shows on both sides: the add-on checks in every 3 s (GET `/api/live/build`, a bpy timer) and its panel says "Linked to <corvette>", "Editor open, LiveLink off" or "isn't running"; the page polls `/api/live/status` and shows "Blender is linked (file.blend)", and Shipwright in the sidebar gets a Live pill while it's on. Turning it on opens a "LiveLink is on" dialog that offers the corvette's .blend (`liveOnDialog`): each corvette remembers the .blend its build came from in `live-files.json` (key: account folder|slot|name, `/api/live/files`), updated by every build Blender sends and by Choose (`/api/live/pick`, the Windows file dialog; `HSE_PICK_FILE` in tests); `/api/live/open` starts Blender with it. The corvette list shows each one's file. The link ends with the editor: `liveShutdown` removes live.json when the app exits. Wrong-corvette guard (`liveConfirmTarget`): each .blend stores its corvette in scene properties `harmonious_target_slot`/`harmonious_target_name`, picked from the add-on's "This file updates" list (fed by `corvettes` on GET `/api/live/build`, sent by `liveArm`); picking one other than the armed corvette warns in Blender. A build whose target isn't the armed corvette gets "Which corvette?" (Don't write / Switch LiveLink); a .blend with no target that isn't the corvette's linked file gets "Put this build in X?"; a confirmed write returns `target` and the add-on keeps it. Each arrival shows a card at the top of the window (`liveArrival`, `#liveNote`, 12 s, errors 30 s), a Last build box in the LiveLink panel, and a pulse on the corvette's card. `test/e2e/test_live.js <dir>` runs the add-on in bpy 4.5 against the app.
- Biome odds (`biomeOdds`, a "Biome odds" row in the Coordinates prediction): the item library (v4, `parseBiomes`) reads `metadata/simulation/solarsystem/biomes/biomelistperstartype.mbin` from Precache (GcBiomeListPerStarType: StarType[5] of 17+17 floats, AbandonedYellow 0x2A8, LushYellow 0x330). Odds per star colour and galaxy kind (`galaxyKind`: every 20 galaxies, lush 10/12, harsh 3/15, empty 7/19; yellow stars in lush galaxies use LushYellow, in empty galaxies AbandonedYellow), exotic kinds summed; prime planets have their own `PrimeBiomeProbability` list (not shown); not which biome a given planet gets. Checked 2026-10-30 against the owner's real table. `go test -run TestParseBiomes` (HSE_TEST_BIOMES=<file> also reads a real one).
- New saves from the game (`diskCheck`, `showNewer`, `DISK`): the desktop page lists the account folder every 3 s and on focus. On the save list it re-lists when anything changes; with a save open, a save file newer than the baseline taken at open shows the `#diskNote` card offering to open it (asks first if there are unsaved edits). Our own writes reset the baseline. `test/e2e/test_disk.js <dir>`.
- Plain editors (Phase 6, "easier editing" block in `src/app.html`): `PAGES.difficulty` (`DIFF_GROUPS`, values from libMBIN's `Gc*DifficultyOption` enums; a changed preset sets `S.diffPreset`, written to meta byte 344 by `patchMeta`), `PAGES.standing` (`STANDINGS`/`MILESTONES` in `^GLOBAL_STATS`; IntValue or FloatValue kept as found), `PAGES.knowledge` (KnownTech/KnownProducts/KnownSpecials, and words: `KnownWordGroups` entries `{Group, Races[9]}` indexed by `GcAlienRace`), `PAGES.bases` (bases without `PlayerShipBase`, settlements `SettlementStatesV2` with `SETTLE_STATS`), `PAGES.companions` (`Pets`, traits -1..1, moods and trust 0..1, floats written with a decimal point via `FL`), `frigatesPanel` on the Freighter page (`FRIGATE_STATS` = `GcFrigateStatType`). `listDetail` and `tabs` are the shared layout. The find box (`findIndex`/`setupFind`) indexes everything when focused. `test/e2e/test_editors.js <dir>` covers all of it (uses the fakebanks item library from `test_itemlib.js`).
- The item library (`itemlibVersion` 4) also holds words (`nms_dialog_gcalienspeechtable.mbin`, entries 0x68), frigate traits (`frigatetraittable.mbin`, 0x68), settlement perks (`settlementperkstable.mbin`, 0x78) and stat ranks (`metadata/gamestate/stats/leveledstatstable.mbin`, entries 0x610, levels 0x80; checked 2026-10-30 against the owner's real file: 54 entries, 51 kept, names such as Trade Lord, Templar and Traveller of the Atlas resolve; values are still sanity-checked and dropped if odd). All optional: a layout change only loses them. The browser version takes words from Goatfungus's `words.xml` (`parseWordsXml`).
- Rewards (`PAGES.rewards`): `accountdata.hg` + `mf_accountdata.hg` (meta slot 1; uncompressed and without the null terminator, though the meta counts it: `noNull` in the codec) hold `UserSettingsData.UnlockedSeasonRewards`/`UnlockedTwitchRewards`/`UnlockedPlatformRewards`. The account file has its own key mapping (`MAPPING.account`, accessor `ag`), not `g`. The item library (v3) reads `historicalseasondatatable` (expeditions by `DisplayNumber`, entries 0xB8), `unlockableseasonrewards` (0x78), `unlockabletwitchrewards` (0x30) and `unlockableplatformrewards` (0x20). The desktop API reads/writes only save pairs and this pair (`acctFile` in `main.go`). Rewards have their own save button (`saveAccount`); the player claims them on the Space Anomaly. `test/e2e/test_rewards.js <dir> <folder with the account pair>`.
- `tools/extract-nms-item-files.bat` — collects game tables, English text and an icon sample from the owner's install (via HGPAKtool) for developing the reader.
- `vendor/libnom/` — key mapping and hashed-tech list from libNOM.map / libNOM.io. Refresh `mapping_mbincompiler.json` when the game adds keys.
- `ROADMAP.md` — the owner's wishlist sorted into phases. Check it before starting new work and tick items off as they ship.
- `dist/` — built outputs: `nms-save-editor.html` (browser version) and `Harmonious Save Editor.exe`.

## Build
```
node build.js            # dist/nms-save-editor.html + desktop/index.html
./build-desktop.sh       # dist/Harmonious Save Editor.exe (Go 1.22+)
```
Always rebuild both and commit `dist/` so the owner can grab the exe from GitHub.

## Rules for changes
- Never lose data: unedited saves must re-encode to identical JSON; the page re-decodes before every write; the app backs up the pair before replacing it.
- Edit via the key accessors (`g`, `set`, `kOf`) so obfuscated and plaintext saves both work. New fields get the obfuscated key via `NAME2OBF`.
- Keep new slots/items in the same key order the game uses (copy from an existing sibling).
- Owner is on Windows with Steam; Chrome blocks AppData for web pages, so the desktop app is the primary way to use it.
- Look: "Glacial", matching the owner's Portal Glyph Banner. Tokens live on `:root` in `src/app.html` with a dark set under `prefers-color-scheme` and `[data-theme=dark]`. Text is neutral (dark gray in light mode, white in dark mode) and never tinted. The sidebar is in groups (`NAV_GROUPS`, owner's order 2026-10-30: overview/shipwright/coordinates/Dock Yard/hangar; exosuit/multi-tools/starships/freighter/exocraft/companions; bases/storage/cargo; knowledge/rewards/standing/difficulty; item names/raw data), each on a faint tint of its group colour. Each section has its own accent from `SECTION_COLORS` in `src/app.html`: the "Spectrum" scheme the owner chose, sweeping teal, blue, violet, magenta, rose and coral, with mint and slate for the tool pages. Light mode darkens it automatically. New sections get a colour that fits the sweep. Rose `--spark` is reserved for unsaved changes. No yellow. Titles and section labels use the banner's wide-tracked uppercase; everything else is sentence case. Jost is the typeface, bundled from `vendor/fonts/jost` (SIL OFL) and inlined by `build.js`, so no web fonts are loaded.
- Supercharged slots are `SpecialSlots` entries `{Type: {InventorySpecialSlotType: TechBonus}, Index: {X, Y}}` on a technology inventory (`chargedSet`/`setCharged`); the button shows on exosuit, starship and exocraft technology (`canCharge`). The border is steady; the arcs only animate on hover, selection, or once after charging (`S.zap`), because a fully charged grid was too busy. `test/e2e/test_supercharge.js <dir>`.
- Inventories use the game's names and order: Technology (`*_TechOnly`) first, then Cargo (stored as `Inventory`). The legacy `Inventory_Cargo` the game no longer shows is listed as "Old cargo" only when it has items. `invGroup` shows them with a Technology / Cargo / Both switch. Grids keep the game's columns (slot position matters for adjacency) and scale with the window.
- UI copy: plain, sentence case.
