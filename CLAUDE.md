# Harmonious Save Editor

No Man's Sky save editor for Steam/GOG PC saves (Frontiers 3.60+). Owner: Pastullio. GPL-3.0.

## Layout
- `src/codec.js` — save format: LZ4 chunked data file, XXTEA-encrypted meta file, lossless JSON (keeps key order, number lexemes, escapes, raw hashed-ID bytes). Works in browser and Node.
- `src/app.html` — the whole editor UI (vanilla JS, no framework). `build.js` inlines the codec and the key mapping into it.
- `desktop/` — Go app (stdlib plus one vendored library, github.com/klauspost/compress for zstd; keep `desktop/vendor` committed and add nothing else) that serves the page on 127.0.0.1 with a per-run token and an API to list/read/write save pairs. Windows build is the main deliverable. The app keeps the fixed port 47821 (the browser keeps localStorage and IndexedDB per origin, so a different port forgets the theme, cover view, part picks and cover stills): if the port is taken by a running editor of the same version (`/hse-hello`), `handOver` opens a window on that one and exits, else it waits up to 10 s for the port before falling back to a random one (owner, 2026-11-01: light and dark kept swapping between launches). The window is the editor's own (WebView2; see the Own window line below); the fallback is an Edge/Chrome `--app` window with its own profile, opened centred on the main screen's work area (`windowPlacement` in `window_windows.go`, shrunk on small screens; `forgetWindowPlacement` drops the placement the browser saved in the profile so it doesn't override that). Taskbar: `tagEditorWindows` finds the window (class `Chrome_WidgetWin_1`, title "Harmonious Save Editor", every 1.5 s) and gives it its own AppUserModelID (`Pastullio.HarmoniousSaveEditor`) with the exe as relaunch icon and command, plus WM_SETICON, so it isn't grouped under Edge's icon (owner, 2026-11-01); Edge puts its own ID back, so `windowAUMID` checks it every pass and it is re-applied, and `setProcessAUMID` gives the exe the same ID.
- Own window (released 2026-11-04; the last Edge-window version is tag `edge-window-stable`): `desktop/webview_windows.go` opens a Win32 window with WebView2 inside (COM through vtables, stdlib only; Microsoft's `WebView2Loader.dll`, BSD, embedded from `desktop/webview2/` and written to the app folder). Data in `%LOCALAPPDATA%\HarmoniousSaveEditor\webview`; on first start `migrateBrowserData` copies Local Storage and IndexedDB from the Edge profile (`window\Default`). X asks the page (`hseCloseRequest` → `close-ack`, then the Exit button's flow; no answer in 4 s closes); page messages over `chrome.webview.postMessage`: `ready`, `close-ack`, `exit`, `theme:dark|light` (dark title bar, remembered in `window.json` for the background colour). Other sites and `target=_blank` links open in the default browser. A second start POSTs `/hse-focus`. The window gets the exe's icons by WM_SETICON and no AppUserModelID or relaunch properties, so Windows treats it as the exe's (with them the taskbar showed a blank icon, owner 2026-11-04). Falls back to the Edge window when the runtime is missing or it fails within 30 s; `HSE_WINDOW=edge` or a `use-edge-window` file in the app folder forces Edge. Test builds were stamped `dev-webview-N` (any `dev` version skips self-updates). `test/e2e/test_native.js <dir>` checks the page side with a stand-in bridge.
- `desktop/render.go` + `desktop/render_cover.py` — corvette cover renders: finds the owner's Blender and Charon Forge (Blender extension, GPL-3.0, github.com/xX-Charon-Xx/charon_forge), runs `blender -b --factory-startup --python render_cover.py`, caches PNGs in `%LOCALAPPDATA%\HarmoniousSaveEditor\covers\<build hash>.png`. Never bundle Charon Forge's game-derived models; always read the local install. Extra camera angles (`coverViews` in render.go: front, side, back, top) render together in one Blender run (`/api/render?views=1`, job `<key>-views`, files `<key>-<view>.png`, `/api/cover?view=`); the Hangar's view chips (`COVER_VIEWS`, `#hViews`) pick one, remembered per build in localStorage `hse-render-view`. Automatic renders (`autoRenderCorvettes`, 6 s after a save opens): corvettes without a cover are rendered one at a time when Blender and Charon Forge are found and `settings.autoRender` isn't false (Cover settings). `test/e2e/test_render_views.js <dir>` (real renders through bpy and Charon Forge).
- `desktop/itemdb.go` — item names and icons from the owner's own Goatfungus `NMSSaveEditor.jar`: found on the PC (Downloads, Desktop, Documents, Program Files…), remembered in `settings.json` as `itemdb`, served from inside the jar (`/api/itemdb`, `/api/itemdb/items.xml`, `/api/itemdb/icon`). Never bundle the jar's data or icons. The browser version reads a picked jar into IndexedDB instead.
- `desktop/profiles.go` — loadout profiles as JSON files in `%LOCALAPPDATA%\HarmoniousSaveEditor\profiles` (list, write, delete, reveal). Profiles use plain key names (`toPlain`/`fromPlain` in the page) so they work with obfuscated and plaintext saves. `desktop/slots.go` — copy a save into an empty slot (never overwrites) and zip a whole account folder.
- `desktop/gamefiles.go` + `desktop/itemlib.go` — the app's own item library, built from the owner's game install: HGPAK archive reader (format from HGPAKtool, MIT), MBIN table reader (field offsets from MBINCompiler's libMBIN, checked against each template GUID), BC7/BC1/BC3 DDS decoder (port of Pillow's BcnDecode.c). Reads the product (plus base-part and customisation), substance, technology and procedural-technology tables and the English language files, converts icons to 128 px PNGs, and caches all of it in `%LOCALAPPDATA%\HarmoniousSaveEditor\itemlib`. Built automatically on first start and rebuilt when the archives change. When a game update changes a table layout the GUID check fails: update the offsets from the newest libMBIN. Goatfungus's jar (`desktop/itemdb.go`) is only a fallback now. Never commit game files.
- `desktop/models.go` — real models: SCENE.MBIN trees (REFERENCE nodes pull in parts; siblings named `_Group_Option` are alternatives, `xRARE`/`Shape`/`LODn` handled in `optionOf`), GEOMETRY.MBIN.PC / GEOMETRY.DATA.MBIN.PC streams (magic DDDD…; positions half4 at stride 16, then vertex data and indices, 16-bit per mesh whenever it has ≤65,536 vertices whatever the header says). Meshes under a JOINT are skinned and already in model space, so they skip the joint transforms. Effect meshes (glow, lights, shadow planes, decals; see `effectMaterialRe`) and shield/effect/decal references are left out. `/api/model/parts` gives the choice tree, `/api/model/mesh` one binary triangle mesh (`HSEM`; `only=<group>&depth=n` keeps just the geometry under that group's chosen option, n counting same-named groups from the outside, for the picker's part pictures). Picks are keyed by group name; a name that repeats at different depths (`_MultiTool` inside `_MultiTool`) stores one choice per depth joined with `|` (`pickFor`, `merge` in `partsDialog`). The picker (`partsDialog`) shows each choice as a tile with its own picture, nested groups indented under the choice they belong to and named without the parent's code (`partLabel`, `PART_WORDS`). The page draws it with WebGL2 (`GL3D`) and stores the owner's part picks in IndexedDB (`parts:<cover key>`). Covers are made fresh on every page draw, so `COVER_MEM` keeps each cover's model, still and render by cover key for the session (`coverFromMemory` in `paintCover`), and `saveStill` keeps a still picture of each model in IndexedDB (`still:<mesh url without token>`) that `loadModel` shows at once while the model loads; the Dock Yard's `libFlow` fills every cover in the background (nearest first) and loads ship models as well as corvette renders.
- Corvette hologram (`paintHoloBlocks`, `holoGroup`, `HOLO_COLOURS`, `holoLegend`): each part is a shaded block at its real size, coloured by type (cockpit, engines/wings, weapons, shields, reactors, gear, bays, hull/plating in the class tint, decor). Sizes from `desktop/partboxes.go` (`/api/model/boxes`): the building table (`basebuildingobjectstable.mbin`: ID 0x208, PlacementScene 0x158, SinglePartID 0x178, entries 0x2B8 from Objects at 0x1C8; `basebuildingpartstable.mbin`: StyleModels[0].Model) gives each part's scene, and the box is its collision boxes, or its mesh AABBs when it has none; the shared 15 m exterior box is drawn as one module cell; `holoGuessBox` until sizes arrive or without the game. The real hull can't be drawn from the game files: placement scenes hold every variant and the game picks hull pieces at run time from snap-point rules (ROADMAP). `test/e2e/test_corvette_holo.js <dir> <PCBANKS with the corvette modules>`; `HSE_TEST_TABLES=<tables folder> go test -run TestParsePartScenes`.
- Coordinates page (`PAGES.coords`, `Place` in `src/app.html`): portal code (planet, system, Y, Z, X), galactic address (X+0x7FF:Y+0x7F:Z+0x7FF:system) and the packed 64-bit address used by discovery records and bases (from the low bits: X 12, Z 12, Y 8, galaxy 8, system 12, planet 4; parse with BigInt). Warp writes `UniverseAddress`, moves the old one to `PreviousUniverseAddress` and sets `SpawnStateData.LastKnownPlayerState` to `InShip`. Arriving at a base (`arrivalSpots`, `placeAtSpot`, `warpTo(p, spot)`): bases and teleport endpoints store a planet-relative `Position`; the spawn fields are star-relative, so the planet centre comes from `PlanetPositions[planet - 1]` (same order as `PlanetSeeds`). `savedPlanetCentres` only trusts them when `PlanetSeeds` matches nms-core's predicted seeds for the save's address; `rememberPlanets` keeps them in IndexedDB (`planets:gi:x:y:z:sys`) so other saves can arrive there. Player 2 m above the base centre facing its `Forward`, ship hovering 40 m up, `OnFoot`. Checked on the owner's save made at a base (121 m from where they stood). Arriving on the freighter (`placeAboard`, `ABOARD`): writes `FreighterUniverseAddress`, clears `FreighterDismissed`, state `AboardFleet`; player and ship positions are freighter-relative, copied from the owner's save made aboard a capital freighter; the death respawn point is star-relative beside `FreighterPositionInSystem`. `test/e2e/test_arrive.js <dir> <folder with a save made at a base> [other save folder] [plain JSON of a save made aboard]`. Glyph art comes from the owner's Portal Glyph Banner (`src/assets/glyphs/g0-gF.png`, inlined by `build.js`, drawn as CSS masks). `test/e2e/test_coords.js <dir>` tests it on a copy of a real save. System prediction (`predictSystem`) uses `vendor/nms-core` (MIT, unchanged copies; see its README for provenance), bundled by `tools/bundle-nms-core.js` into `NMSGEN` with the letter map gzipped (unpacked with DecompressionStream on first use). Don't use nms-core's `economy.js`, the biome/sentinel `opts` of `planetName()` or `sizes`: they aren't game-accurate.
- Dock Yard (the ship library; section id `library`, the page's "library" source is the Ship storage folder): `desktop/ships.go` (`/api/ships`, `/api/ships/file`, `/api/ships/index`, `/api/ships/folders`) keeps `Documents\Harmonious Save Editor\Dock Yard\{Ship storage,Garage,Deleted}` (an older `Ships\Library` is moved across once by `migrateShips`) and `library.json` (tags, favourites, links, notes, cached summaries keyed `src|root|path`); linked folders (`settings.shipFolders`) are read only, enforced in `shipPath`. Page: `PAGES.library`, `ShipLib`, `parseShipFile`, `putShipInSave`, `garageCapture` (runs when a save opens). Garage versions: `shipFingerprint` hashes `shipEssence` (model, name, class, colours, base fields, tech Id+Index, build without part Timestamps; leaves out parking spot, tech charge/damage, cargo, and the corvette base's GalacticAddress/Position/Forward/UserData/LastUpdateTimestamp; numbers compared by value), and a capture is skipped when any Garage file already has that print (`ShipLib.garagePrints`, summaries cached in library.json with `SUM_V`). Captures run when a save opens and after Save to game / a LiveLink write; opening the Dock Yard runs `garageCapture({onlyNew: true})`, which only keeps ships added since the save was opened (identity not in `S.openIdents` nor the Hangar), so a deleted Hangar copy doesn't come straight back (owner, 2026-11-03: a corvette added in slot 7 was missing). One unreadable ship doesn't stop the rest. `garageGroups` shows one card per ship (`shipIdentity`: model + seed, plus `Owner.TS` of the build for corvettes, which share seeds); Dock Yard and save linked both ways (owner, 2026-11-01: it felt like a gallery): `saveShipSlots` maps the open save's ship identities to slots, `dockSlotOf` (also `S.dyPlaced`, ships just put in from here, as a corvette's put-in build takes this player's owner stamp), `dockActions` is the bar above Cover Flow (`.dy-acts`: Edit ship / Edit build via `editShipAt`, Load ship into game… (= put in the open save), Details, Favourite; `putShipInSave` returns the slot), a loaded ship's cover says "Loaded, slot N" (Cover Flow item `tag`, `.cf-tag`, also redrawn by `refresh`) and loaded ships sort first by slot; matching also takes model + seed + name (`looseId`, any version), as a corvette's owner stamp can change in the game, grid cards show the same + Edit ship or Load ship into game…, and Starships' "Versions in the Dock Yard" (`showInDockYard`, `L.openKey`) opens the ship's Garage card. `libDetail` lists versions newest first, copies of a version can be moved to Deleted ("tidy"), and group meta (tags, star, notes, cover key) lives under `garage|ship|<identity>`. A corvette's build is the `PlayerShipBase` in `PersistentPlayerBases` whose `UserData` is the ship's slot index; moving a corvette means re-pointing `UserData`. TAZ's `.nmsship` is a zip of `objects.json` (the build's Objects), `so.json` (the ShipOwnership entry) and `ccd.json` (the slot's `CharacterCustomisationData` entry; ships 1-6 are indexes 3-8, ships 7-12 are 17-22, per libMBIN's `CustomisationDataTypeEnum`); `unzip`/`zip` in the page use DecompressionStream/CompressionStream('deflate-raw'). A `.so` is just the ship entry. `test/e2e/test_library.js <dir>` covers it on a copy of a real save.
- Shipwright (`PAGES.shipwright`): corvette build tools. `partGroup` sorts parts by the game's own description ("Corvette Reactor Module", "Corvette Main Engine"…, from the item library) with ID prefixes as the fallback; `tunedOrder` is a stable sort in TAZmd's documented priority order (tazmd.nl/corvette-optimizer; our own code). Paste/load replaces a build's Objects only, keeping the base's UserData, BaseType, name and owner, and puts each part's fields in the game's order (`inGameOrder`). `addCorvette(slot)` copies a ship entry already in the save (BIGGS model, new seed, C class, empty inventories) and adds a `PlayerShipBase` (copied from another corvette base for the layout, owner taken from the player's bases) with `STARTER_PARTS`. `test/e2e/test_shipwright.js <dir>` (needs the fakebanks item library for names).
- Your traveller (owner, 2026-11-10; `desktop/traveller.go`, `travellerCard`/`travellerGroups`/`travellerShare` on the Exosuit page): the save's `CharacterCustomisationData[0].CustomData.DescriptorGroups` (`^TORSO_VYK`…) are group IDs; `charactercustomisationdescriptorgroupsdata.mbin` (GcCustomisationDescriptorGroups 0x6E1D4A06924711BB: sets at 0x30 of 0x38, groups of 0x108 with Descriptors at 0x40 and GroupID at 0x50) turns them into option nodes of `models/common/player/playercharacter/playercharacter.scene.mbin`, which `buildMesh` picks via `picks._names` (`/api/model/traveller` gives scene + names). `/api/model/traveller/glb` writes a binary glTF (`writeGLB`): one primitive per game material, the scene's JOINT nodes as glTF nodes (local from their rest pose, inverse bind matrices from it), and per vertex 4 bone slots (vertex stream semantic 5, bytes) and weights (semantic 6, half4) mapped through the geometry's SkinMatrixLayout from the MESH's FIRSTSKINMAT (the player's meshes sit beside the skeleton, so a mesh with FIRSTSKINMAT < LASTSKINMAT and bone data counts as skinned; `meshOut.collect`/`meshPart`); the root is turned 180° so Blender's front view sees the face. Joint rest poses come from the geometry's InvBindMatrix (stored column-major: transpose, then invert; `bindPose`), not the scene's JOINT transforms, which don't match the mesh (owner 2026-11-10: finger bones floated beside the body). ## Rules for changes

- Edit via the key accessors (`g`, `set`, `kOf`) so obfuscated and plaintext saves both work. New fields get the obfuscated key via `NAME2OBF`.
- Keep new slots/items in the same key order the game uses (copy from an existing sibling).
- Owner is on Windows with Steam; Chrome blocks AppData for web pages, so the desktop app is the primary way to use it.
- Look: "Glacial", matching the owner's Portal Glyph Banner. Tokens live on `:root` in `src/app.html` with a dark set under `prefers-color-scheme` and `[data-theme=dark]`. Text is neutral (dark gray in light mode, white in dark mode) and never tinted. Copy/Paste use `S.clip` (slot clones; paste fills from that slot onwards, tech grids only take tech), Duplicate goes to the next empty slot; Move to lists `fitTargets` (technology only where `techFit` allows it; also used by the bulk inspector). `test/e2e/test_slotmenu.js <dir>`.
- Leaving (owner, 2026-11-03): in the own window the X calls `hseCloseRequest` (Exit button flow); in the Edge fallback the browser's beforeunload box can't have custom buttons, so its handler also queues `leaveDialog()` (only runs if the page stays, i.e. Cancel) with Keep editing / Exit without saving / Save & exit; `#exitBtn` (app only) asks the same. `saveAndExit` writes the save (asks only if the game is running) and dirty rewards (`saveAccount`), then `exitApp` → `window.close()` (works in the --app window, whose history has one entry) or a toast. `test/e2e/test_exit.js <dir>`.
- Inventories use the game's names and order: Technology (`*_TechOnly`) first, then Cargo (stored as `Inventory`). The legacy `Inventory_Cargo` the game no longer shows is listed as "Old cargo" only when it has items. `invGroup` shows them with a Technology / Cargo / Both switch. Grids keep the game's columns (slot position matters for adjacency) and scale with the window.
